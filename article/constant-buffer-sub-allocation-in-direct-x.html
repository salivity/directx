Constant Buffer Sub-Allocation in DirectX

In DirectX 12, constant buffer views (CBVs) must adhere to strict 256-byte memory alignment constraints, a requirement that frequently leads to severe memory waste when handling small uniform structures. By utilizing sub-allocation—carving dynamic data blocks from a single, large pre-allocated buffer—developers can tightly pack uniform updates across 256-byte boundaries rather than provisioning individual GPU resources. This technique satisfies hardware alignment rules, mitigates internal and external memory fragmentation, and reduces resource creation and tracking overhead on the CPU and GPU.

The 256-Byte Alignment Constraint

DirectX 12 requires that every constant buffer view begin at a GPU virtual address that is a multiple of 256 bytes, defined by the constant D3D12_CONSTANT_BUFFER_DATA_PLACEMENT_ALIGNMENT. Shaders frequently consume far less data than this limit; for example, a single transformation matrix consumes 64 bytes, and a simple material color property may require only 16 bytes.

If an application allocates a standalone ID3D12Resource for each small uniform payload:

  • Internal Padding Waste: The application must pad the 16-byte or 64-byte payload to 256 bytes to satisfy the view configuration.
  • Heap Granularity Waste: Placed or committed resources in DirectX are subject to heap alignment boundaries—typically 64 KB for standard buffers. Creating separate resources for individual draw-call constants results in tens of kilobytes of unaddressable, unused memory per call.

How Sub-Allocation Works

Sub-allocation resolves this inefficiency by employing a user-space memory manager, such as a linear or ring allocator, backed by a large single allocation in an upload heap (e.g., a single 64 MB buffer).

Instead of creating individual resources, the engine calculates the required size of each uniform block, rounds that size up to the nearest 256-byte multiple using a simple bitwise alignment formula:

\[\text{AlignedOffset} = (\text{CurrentOffset} + 255) \ \& \ \sim255\]

The engine then copies the uniform data into the mapped pointer at AlignedOffset and advances its internal pointer. To bind the data, the application passes the base address plus the aligned offset directly to a root descriptor using SetGraphicsRootConstantBufferView, or creates a descriptor targeting the specific sub-allocated range.

Mechanics of Waste Reduction

Sub-allocation eliminates memory bloat through several key mechanisms:

  1. Eliminating Heap Page Waste: Instead of paying the 64 KB page-alignment penalty for every uniform update, thousands of updates share the same underlying memory pages. A 64-byte payload only accounts for 256 bytes of total usage (including alignment padding), rather than 64 KB.
  2. Minimizing Inter-Payload Gaps: By advancing strictly in 256-byte increments, uniform data blocks sit contiguously in memory. While any payload under 256 bytes still incurs some padding to reach the alignment mark, this waste is bounded to a maximum of 255 bytes per sub-allocation, rather than whole system pages.
  3. Data Packing and Coalescing: For updates that belong to the same draw call or shader pass, multiple uniform parameters can be packed into a single structure prior to sub-allocation. If a draw call requires three separate matrices (192 bytes total), packing them into one sub-allocated 256-byte block yields only 64 bytes of waste, compared to 576 bytes if each matrix were bound to separate 256-byte aligned regions.
  4. Reduced Driver and Kernel Footprint: Allocating memory in user-mode via pointer arithmetic avoids creating kernel-level resource tracking structures, descriptor table bloat, and page table updates, drastically lowering the application's overall working set and cache footprint.
