Understanding Deferred Shading and MRTs in DirectX

Deferred shading is a rendering technique designed to handle complex scenes with numerous dynamic light sources by separating geometry processing from lighting calculations. Instead of computing the shading for every polygon as it is rasterized, deferred shading stores surface attributes in a set of intermediate textures known as the G-buffer during an initial geometry pass. This article explains the fundamentals of deferred shading, how it solves performance bottlenecks associated with traditional forward rendering, and how it leverages Multiple Render Targets (MRTs) within DirectX to efficiently populate the G-buffer.

The Problem with Forward Shading

In traditional forward shading, each object in a scene is transformed, rasterized, and shaded in a single pipeline execution. If a scene contains \(M\) objects and \(N\) dynamic lights, the theoretical worst-case rendering complexity scales to \(O(M \times N)\).

This approach introduces significant overdraw. Pixels shaded for occluded geometry are ultimately overwritten by objects closer to the camera, wasting expensive lighting and material calculations. While depth pre-passes can mitigate overdraw, forward shading still requires switching shader variants or looping through complex light arrays for every rendered mesh.

The Deferred Shading Paradigm

Deferred shading circumvents this overhead by decoupling geometric rasterization from illumination. The process is divided into two primary stages:

  1. The Geometry Pass: The scene’s geometry is drawn without performing any lighting calculations. Instead, surface attributes—such as diffuse color, world-space or view-space normals, roughness, metalness, and depth—are written directly to separate screen-space textures.
  2. The Lighting Pass: A full-screen quad or bounding light volumes are rendered. Shaders read the stored material and geometric data from the intermediate textures, evaluate the lighting equations only for visible pixels, and output the final image.

By deferring the lighting to screen space, the computational complexity drops to \(O(\text{geometry}) + O(\text{lighting})\). Shading cost becomes proportional to screen resolution and the screen-space coverage of the lights, rather than the total geometric density of the scene.

The Role of Multiple Render Targets (MRTs)

To make deferred shading viable, the geometry pass must write multiple surface properties in a single draw call. Rendering the scene multiple times to capture each attribute individually would saturate the CPU and GPU with redundant draw calls and state changes.

DirectX enables this through Multiple Render Targets (MRTs). MRT allows a single pixel shader to write output to multiple render target views (RTVs) bound to the Output Merger (OM) stage simultaneously.

Implementing MRTs in DirectX

In DirectX (such as Direct3D 11 or 12), using MRTs involves configuring both the API pipeline state and the High-Level Shader Language (HLSL) code:

1. Pipeline Configuration

The application allocates several textures that match the screen dimensions, typically utilizing optimized formats to conserve memory bandwidth:

  • Albedo / Base Color: DXGI_FORMAT_R8G8B8A8_UNORM
  • Normals: DXGI_FORMAT_R16G16B16A16_FLOAT (or encoded into two-channel formats)
  • Material Properties (Roughness, Metalness, Ambient Occlusion): DXGI_FORMAT_R8G8B8A8_UNORM
  • Depth: Managed via the standard Depth-Stencil View (DXGI_FORMAT_D24_UNORM_S8_UINT or DXGI_FORMAT_D32_FLOAT)

In Direct3D 11, these textures are bound simultaneously using ID3D11DeviceContext::OMSetRenderTargets. In Direct3D 12, descriptor tables containing CPU descriptors for each RTV are bound via OMSetRenderTargets inside a graphics command list.

2. HLSL Pixel Shader Output

The pixel shader uses semantic bindings (SV_Target0 through SV_TargetN) to route different data elements to their respective textures in parallel:

struct PixelOutput
{
    float4 Albedo    : SV_Target0;
    float4 Normal    : SV_Target1;
    float4 Material  : SV_Target2;
};

PixelOutput GeometryPassPS(VertexOutput input)
{
    PixelOutput output;
    
    // Sample textures and calculate attributes
    output.Albedo   = diffuseTexture.Sample(samplerState, input.UV);
    output.Normal   = float4(normalize(input.Normal), 1.0f);
    output.Material = float4(roughness, metalness, ambientOcclusion, 1.0f);
    
    return output;
}

The depth is automatically written to the bound depth-stencil buffer by the hardware rasterizer, eliminating the need to write it manually to an additional render target.

Executing the Lighting Pass

Once the G-buffer is populated via MRTs, the DirectX runtime unbinds the render targets and binds them as Shader Resource Views (SRVs) for the lighting pass.

In the lighting pass, pixel shaders reconstruct the 3D position of each pixel using the screen UV coordinates, the depth buffer value, and the inverse view-projection matrix. With position, normal, and material data available on demand, the shader evaluates analytical light equations (such as Cook-Torrance or Blinn-Phong) across arbitrary numbers of point, spot, and directional lights.

Technical Trade-Offs

While deferred shading paired with MRTs handles dense lighting scenarios efficiently, it introduces specific engineering challenges:

  • High Memory Bandwidth: Reading and writing multiple high-resolution textures significantly increases memory bandwidth requirements.
  • Hardware Anti-Aliasing (MSAA): Traditional hardware-based multi-sampling does not work cleanly with MRT setups, requiring specialized MSAA resolve passes or alternative post-process techniques like FXAA or TAA.
  • Transparency: Because the G-buffer stores only the closest opaque surface attributes per pixel, deferred shading cannot natively handle transparent geometry. Transparent objects must be rendered afterward using a standard forward rendering pass on top of the deferred lighting results.
